## Phase 6 — Export and Deployment

Executing the C++ inference engine on the Jetson Orin Nano required navigating extreme OS-level and runtime bottlenecks that do not show up on a datacenter GPU. The standard PyTorch loader path, if naïvely applied, encapsulated highly compressed 2-bit (and mixed-tier) values inside wide containers and, worse, encouraged **monolithic** materialization of the full language-model checkpoint; that produced the familiar **~17 GB PyTorch container** failure mode where simply attempting to load the artifact drove **heap exhaustion** long before any useful forward pass.  

The `profile_jetson.py` script attacked that failure mode on the **PyTorch / profiling** side by combining a deliberate **`mmap` bypass** in `torch.load(..., mmap=True)` with a **layer-by-layer replacement** strategy so RSS climbed in a controlled staircase instead of a cliff; the script logs RSS and CUDA allocated memory at each milestone and refuses to pretend a non-zip checkpoint is magically page-backed when it is not (it prints an explicit warning when `mmap` may be ineffective). That work was about **surviving inspection and staged PT-side validation on Orin-class RAM**, not about the final GGUF consumer.  

Independently, the **native C++ runtime** (`bmo_load_model` / `bmo_prepare_device_packed_tensors`) attacks the same physical reality from the other direction: weights are **`pread` into explicit scalar and “big” host pools** (not lazy OS paging of the GGUF file), and on **`BMO_JETSON` builds** the large pool is **`cudaHostRegister`’d** so kernels can see a **mapped, pinned** view—i.e. the zero-copy style read path across unified memory that you were aiming for, but implemented **inside `libbmo.so`** rather than inside `torch.load`. The two stories rhyme: **mmap / staged load on the PT funnel**, **pinned mapped pools on the GGUF funnel**.

The pipeline required forensic debugging to resolve **four distinct GGUF / parity bugs** that would otherwise have made any C++ result untrustworthy. First, the `verify_depth.py` diagnostic initially suffered a **`depformer_emb` offset / routing error** at step 0—text embeddings were being applied where only the **audio codebook channels (steps 1–15 in the depth schedule)** should have contributed—so the PyTorch reference and the C++ harness were not even solving the same local problem until that was corrected. Second, `export_bmo_gguf.py` had been **silently incomplete**: it dropped a batch of missing tensor exports (you counted **17**, including critical **output codebook heads**), which only surfaced as subtle numerical drift until we added **explicit export calls** and a **hard completeness check** that fails the build instead of emitting a hollow GGUF. Third, a **`ggml_add` broadcasting** crash in the depth RMS path traced to a **layout mismatch**: the depth norm tensor arrived effectively as a **3D** view `((1, 1, 1024))` where the graph expected something **`ggml` could broadcast like a 1D `(1024,)` slab**; flattening / reshaping at the ABI boundary aligned host memory with what the depth graph builder assumed. Fourth, FP32 tensor bloat in the exporter was tamed with the **`preserve_half=True`** directive on the dense tensors that did not need full float32 fidelity, which is what let the **v12 ~7.69 GB GGUF** land as a physically shippable artifact instead of an inflated float dump.

**Where things stand now (current state, as of this writing).** The C++ side is **no longer a scaffold that “cannot run depth”**: `bmo_forward_depth` is fully wired (`bmo_api.cpp` builds and executes `bmo_build_depth_graph`, copies `audio_logits`), and the **temporal stack** is driven through the same **`ggml` graph + custom CUDA intercept** pattern documented in `REPORT_C_CPP_JETSON_CURRENT_STATE.md`—fused **SEPTQ dequant–matvec** (`bmo_cuda_kernels.cu`, proto path for **packing_version ≥ 5** in `bmo_cuda_kernels_proto.cu`), **interleaved RoPE**, **RMSNorm / residual / SwiGLU** hooks, and a **Jetson-specific** staging story (`gpu_staging_pool`, `n_ctx` capped at **1024** in-tree to keep KV inside unified memory). On the Python side, **`bmo_inference.py stream`** was rewritten for **`LMGen` parity with `moshi.offline`** under `BMO_USE_CPP=1` (`patch_lm_for_bmo`, warmup, **`bmo_engine.reset()` after warmup**, `step_system_prompts`, per-frame `lm_gen.step`, Mimi-encoded user silence when audio runs out)—so the **driver** is finally chasing the same delay ring and depformer semantics as the reference server instead of a hand-rolled token path that produced garbage audio.

What is **still** honest about Phase 6 is the **performance gap**, not functional emptiness: on Jetson we can **bring the full quantized model resident** and exercise the fused CUDA path, but measured end-to-end behavior remains **orders of magnitude slower** than a native PyTorch step on an H100 in the regime you quoted (**~800 ms** on the Orin-class bring-up you measured versus **~80 ms** for the H100 PyTorch reference). Part of that is physics—Orin Nano memory bandwidth and unified-memory contention versus HBM on H100—and part is engineering debt: **`kDefaultWorkMem`** is only **1 GiB** on Jetson versus **2 GiB** on discrete hosts, graph rebuild strategies per step, Python/Mimi overhead when running the hybrid stack, and the fact that **steady-state decode latency** still needs a disciplined profiling pass separate from “does `libbmo.so` load.” **GGUF vs PyTorch logit parity** is also a live concern: session notes record periods where C++ text logits looked **static across frames** until the Python prefill path was aligned with Moshi’s sine-on-user-channel semantics; treating **audio quality on Jetson** as *closed* without a fresh listening test would be premature.

So Phase 6’s status line is: **export and static correctness largely won; deployment and latency still in progress**—the artifact ships, the engine runs depth, the driver matches `LMGen`, but **Orin Nano is not yet “H100-fast,”** and the last mile is profiling, KV/work-memory budgeting, and on-device validation rather than proving the existence of CUDA kernels we never wrote.

### Optional footnote (if your examiner nitpicks “mmap”)

The **GGUF loader** in `bmo.cpp` comments “init without mmap” in the GGUF sense (metadata context has `no_alloc`), then **explicitly reads tensor bytes**; that is **not** the same mechanism as `torch.load(mmap=True)`. Both are valid responses to the same underlying constraint—**do not explode RSS with a single eager materialization**—implemented at different layers of the stack.
